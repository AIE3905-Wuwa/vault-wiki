# Agent behavior analysis & feedback protocol

> L-layer home of the #34 ruling (C variant): the session is the full record, the issue carries the standardized artifact. Reader class: agents (via deployed copies) and developers. The analysis is generated by the agent itself, from its own loop context. Written 2026-10-13.

## Feedback handling — the behavior face, now declared

When the user reports dissatisfaction with agent behavior:

1. **Immediate fix first** — stop the offending pattern in-session, never continue it while analyzing
2. **Judge the responsible layer** — plugin constraint? framework? pure execution? Not a plugin/kernel matter → no analysis: respond to the user directly
3. **Consent gate** — if it may be a plugin/kernel problem, offer the self-audit to the user (recommended, never forced); start only on consent
4. **Systematic → behavior analysis** (below); one-off → in-session fix + one log line, no issue

This face was previously undeclared (an e-class vacuum live sample, #33's improvised handling).

## Routing — where feedback goes

| Feedback | Destination | Test |
|---|---|---|
| kernel / mechanics / projections / core plugins / framework docs | owfa | framework contract face |
| package member plugins (the bb family, the lark family, …) | the matching `pkg-*` repo | plugin id ∈ `PKG.members`; repo address in the registry INDEX |
| behavior deviations (the #34 face) | wherever the plugin lives | behavior contracts live in PLUGIN.md |
| new plugin proposals | owfa (incubation; moves with the package when it lands) | no owning repo yet |
| unclear | file on owfa; maintainers transfer | fallback (#20 precedent) |

## Triage gate — step 0, not passed means no analysis

① Systematic (the same scene recurs)? ② Reproducible (survives a session change)? ③ Constraint-related (not pure execution)? All three — otherwise: fix in-session + one log line, do not generate an analysis.

## The analysis standard — seven steps

**1. Anchor the event.** Locate the deviation point. Quote verbatim: the user instruction (U layer) + the user's correction.

**2. Reconstruct the behavior chain (fact layer).** From the U-layer instruction, list the actions that actually happened, each with four fields:
- **Action**: what was read / written / called / generated
- **Basis**: a re-read verbatim quote (injection line / AGENTS.md / skill body / PLUGIN.md / session context) — never from memory
- **Owning plugin**: ownerless steps marked "framework / system layer"
- **Trace**: tool-call records / file reads-writes / log entries

Only steps with verifiable traces enter this layer; steps that cannot be confirmed move to step 5 (interpretation).

**3. Expected behavior — two sources, recorded separately.**
- **Declared expectation**: re-read the plugin's L layer (PLUGIN.md behavior contract owns/activates/offers/withholds, the injection line) — quote it, or write "undeclared"
- **User expectation**: the correction verbatim, from step 1

**4. Locate the deviation.** Actual vs expected, item by item. Against declared expectation = a compliance diff; against user expectation = a demand signal. List separately.

**5. Attribution (interpretation layer).** Five classes, multiple allowed, each with a confidence (high/medium/low), a verbatim constraint quote, and the minimal fix if it holds:

| Class | Meaning | Destination |
|---|---|---|
| a constraint defect | wrong / ambiguous / over-executed | fix the plugin |
| b constraint conflict | two plugins give inconsistent instructions | fix the plugins (priority or wording) |
| c not delivered | member-tier exit / skill not loaded | check tier and dependency chain |
| d execution deviation | constraint present, not followed (model side) | not a plugin problem; record, change nothing |
| e spec vacuum | no constraint covers the behavior | add a behavior contract |

**6. Suggested change.** Minimal fix + blast radius (which other scenes depend on this constraint). The agent proposes; weighing and deciding belong to the developer.

**7. Artifact.** Output the full analysis in the `.github/ISSUE_TEMPLATE/agent-behavior.md` format, confirm with the user, file it on the owning repo per the routing table above.

## Red lines

- Quotes must be re-read from the source; reproducing constraint text from memory is forbidden
- The fact layer holds no speculation; all speculation goes to the interpretation layer with a confidence mark
- Attribution classification is mandatory — a blanket "the plugin is buggy" is not accepted
- The `agent-behavior` word root (kept distinct from the user-behavior plugin, per the #34 terminology ruling)
- Artifacts land on GitHub issues, never in the instance wiki
