# cron: deferred-trigger territory

## Design Overview

- **Why it exists**: the 'cadence' of scheduled tasks was once scattered across three places (lark-calendar's session-edition daily refresh, email's optional daily refresh, bili digest reserved), while the executors (harness scheduler / system task scheduler) are per-workspace, machine-bound, and lost on machine change or reinstall — the intent of 'what should be automated when' had no home: the execution side had tasks but no archive, the wiki side had disclosures but no registry. This plugin gives the intent an md home. v0.4 widens the same motive to the condition dimension: cron governs **deferred-trigger unattended intent** — time was merely the first trigger vocabulary; when conditional executors arrived instance-side, the original verbatim repeated (the executor side had watches, the wiki side had no registry — the first real watch carried a self-continuing "re-register me" note that existed only because conditions had no declaration layer)
- **Key rulings**:
  - **Declaration-as-source, executor-as-projection**: an extension of three-projections-one-source into the execution dimension, dissolving the constitutional-principle-4 tension (harness replaceable) — the trigger vocabulary (time = crontab 5-field, condition = the open kind set) is the cross-executor lingua franca, the translation rules belonging to the replay recipes; changing harness / machine / conditional engine = read the declaration pages and replay
  - **Executor-agnostic positioning** (owner ruling 2026-10-08, issue #29): "the plugin must not be limited by any harness; it exists to provide systematic recording and archiving for all deferred-trigger tasks" — every executor (harness scheduler / system task scheduler / conditional executor) is a peer projection: executor names appear only in the replay recipes' deployment-specific translations (usage), never in invariants, the inject line, or block-mapping vocabulary; probing and delivery semantics (inotify / polling / push, at-least-once) stay executor-side — the wiki records intent and traces only
  - **Open trigger vocabulary, fixed machinery**: `time` (the v0.3 schedule key) and `condition` (v0.4) are the first two words; future words (event streams? calendar boundaries?) extend the vocabulary, never the machinery; condition kinds are likewise an open set (first batch file|command|http|process|port|webhook — generic monitoring concepts, no executor's private vocabulary); pattern semantics fixed as no-match→match edge, default any change after baseline
  - **One page per task, pure-directory scheme** (user ruling 2026-10-06, the single-declaration-page proposal rejected): the directory is the full declaration set, no root declaration page — contrast with why the project domain needs `wiki/projects.md` (its container lies outside wiki), while cron task pages are already inside wiki; quick views go through the derived index page
  - **Reconciliation + replay** (user ruling): the declaration is the source of truth — drift enters the check attached audit (the active page set diffed per form against each readable executor-side list), the replay recipe standardized; writing system state and deleting/stopping execution-side tasks both go through user confirmation (following the device attached-audit delegation precedent)
  - **Execution-shape dichotomy lifted** (generalized from the bili ruling into a global criterion): any agent-judgment step → session (unattended session); purely mechanical → script (system task running a connector subcommand, zero quota) — form is orthogonal to trigger, the 2×2 matrix (time|condition × session|script) all four combinations legal; each domain merely tags form, no longer inventing its own cadence disclosures
  - **Unified failure discipline** (lifted from lark-calendar): failed sources report via log, never blocking other tasks; repair delegations one-way derive into todo
  - **Unattended-session SASU-L**: an agent woken by a scheduler or a conditional watch has zero priors — at replay the prompt or watch note must be self-contained (read the task page and execute per the page + report failures via log); the recipe belongs to this plugin's usage; this is the application of 'no knowledge layer leaking into the architecture' at the session boundary
  - **machine anchor left blank**: locates the executing machine in multi-device deployments; keeps only the optional key, no device linkage built; refine through use
- **Position in the family**: a global plugin (cross-cutting deferred-trigger automation), not a domain plugin, does not depend on domain; domain plugins attach and register via the on-demand bridge — this plugin holds 'who is present, what fires it, how to replay and reconcile'; task action shapes belong to each domain (the principle-11 bridge philosophy)

## Structure

- `wiki/cron/<task name>.md` — task page: `cron` block mapping mechanical zone (trigger / action / form / domain / status / last_run / machine optional) + two body sections — `## Task` (action details: which command to call or what the session opening reads, back-linking the owning domain's skill), `## Run Notes` (append-only and convergent: anomalies, repairs, change decisions; normal runs unrecorded — log already has lines, to prevent bloat)
- No root declaration page: the directory is the full set; the derived index includes quick views

## Invariants

- Declaration-as-source: every executor — harness scheduler, system task scheduler, conditional executor — is a replaceable projection; replay and reconciliation both defer to the declaration pages
- Executor names never enter invariants, the inject line, or field vocabulary — the replay recipes (usage) are their only home; trigger semantics declared wiki-side must remain translatable to any executor
- Trigger vocabulary is open (extend words, not machinery); condition declarations carry executor-portable semantics only — what condition, edge, budget, cooldown; never how to probe or deliver
- System-state writes require user confirmation: the script edition landing system tasks or watches, status changes syncing deletes/stops on the execution side — following the device attached-audit delegation precedent
- Normal runs write no task-page history; run notes take only anomalies and changes; last_run is machine-maintained
- status: paused / deprecated pages are never deleted (kept for the record); deprecated tasks remain in the directory for lineage reference
- Three-way boundary: todo one-shot delegations (the human states the trigger) · calendar event facts (what happens when — reality states the trigger) · cron deferred-trigger automation intent, systematically recorded and archived (machine conditions state the trigger); task outputs land per each domain's discipline (e.g. lark-calendar's daily-refresh output goes into the month page's schedule section, bili digest refreshes the digest page)
